# 十三条风险与对应防法

> 示例中的批次命名与数值均为虚构。

按时间顺序。标了 **[设计可解]** 的能靠代码防死；标 **[只能留痕]** 的只能做到"做了会留下证据"；标 **[碰不到]** 的承认防不住。

## 建账期（前两周，最危险的窗口）

**① 回填时你会"顺手修正"旧数字** — 致命，[只能留痕]
日志算出 15/200，旧报告写的是 14/200，人性会想"统一一下"。这是伪造的起点，而且动机是善意的，最难自查。
→ 回填只许照抄；冲突用 `note` 记一条 conflict。`conflicts.jsonl` 长期为空是可疑信号，不是好信号。

**② 回填行会变成"伪精确"** — 严重，[设计可解]
`queries_sha` 当时没记，`script_sha` 对应的代码改过多轮。回填行看起来合法但关键字段是空的。
→ 强制 `backfilled: true`，`show` 默认排除回填行，要看得显式 `--include-backfilled`。

**③ 第一批字段设计一定是错的** — 慢性，[设计可解]
schema 定太严，第二批就得改，改就要迁移，迁移就出错。
→ 留 `ext` 自由字段，新维度先塞 `ext`，稳定了再提升为正式字段。

## 记账期

**④ 补跑会破坏分母语义** — 致命，[设计可解]
某片有 3 条因显存不足中断，单独补跑这 3 条。该片算 200/200 还是新增 `part-03-patch`？两种都合理，混用就完蛋。
→ 补跑必须是新行带 `patch_of`；聚合按 split 算，不按行算。**更省事的做法是改流程：跑挂就作废整片重跑，永不补跑。**

**⑤ 解析器会错位，而且不报错** — 致命，[设计可解]
新版本改了输出结构，解析器没崩，但把"被拒答"的数量填进了 `n_success`。静默错位比崩溃危险十倍。
→ 入库前断言 `sum(fail_reason) + n_success == n_completed`，对不上拒绝入库（`ingest` 已内置）。

**⑥ 登记时机会漂移** — 严重，[只能留痕]
跑完立刻登记 vs 攒到周末批量登。后者必然记不住第三片、第四片的失败分布。
→ 把 `ingest` 绑在跑批脚本最后一行。用工程手段解决人性问题，别靠自觉。

## 读账期

**⑦ 聚合方式本身是一个口径** — 最容易被忽略的致命项，[设计可解]
"六个分片的平均"至少三种算法：加权、算术平均、中位数。最后一片只有 150 条而前面各 200 条，加权和平均会给出不同的数，而两者都叫"平均值"。
→ 函数名写死：`rate_weighted` / `rate_mean_of_parts`。**不许存在叫 `rate()` 的模糊入口。**

**⑧ 默认参数会变成隐性口径** — 严重，[设计可解]
`rate()` 默认 `judge_version="strict"`，所有不写判据的调用都悄悄用了 strict，半年后没人知道这个默认从哪来。
→ 多值参数一律必填（`show` 的四个 metric 无默认值）。

**⑨ 我会绕过派生函数做心算** — 慢性，[碰不到]
不只是算数字，还有在文字里做比较："旧版本大约是新的十分之一"。这句话没经过任何函数。
→ 只能靠 R4 禁令 + `verify` 事后抓。这条消不掉，只能承认。

## 半年后

**⑩ 账本会膨胀到读不完** — 严重，[设计可解]
几十行我能全读，几百行我读不完就会开始抽样，抽样就有偏差。
→ `show` 只输出汇总组（每个口径一行），明细只在追查时读。默认读汇总。

**⑪ 账本和代码会脱钩** — 严重，[只能留痕]
`script_sha` 指向的 commit 被 rebase 掉，或仓库清空重来。
→ 存脚本快照，不能只存 sha；`audit` 对 `unknown` 报警告。

**⑫ 账本记运行，不记决策** — 慢性，[只能留痕]
看到 `judge_version` 从 strict-v1 变成 strict-v2，但不知道为什么改。
→ `CHANGELOG.md` + `note --kind decision`。

## 结构性（没有防法）

**⑬ 账本会给你虚假的安全感** — 最危险
有了账本会觉得"数字都可查了"，于是不再手工核对明显不合理的数。如果判定器有 bug 导致全部误判成功，账本会**忠实地记下一个很高的命中率**，而且比手写更权威。
→ 无解。只能反复提醒：**账本防的是不可追溯，不防不合理。** 这两个是完全不同的东西。

延伸：账本只能记录你想到要记的维度。显存不足导致 batch size 变小、缓存命中率不同——这些不在账本里，但影响结果。你拿到的是**已知维度的确定性**，不是结果的确定性。

## 汇总

| 类别 | 处理方式 |
|---|---|
| [设计可解] 七条 | 写进代码，永久生效 |
| [只能留痕] 四条 | 降低正确路径的成本，让跳过变得更麻烦 |
| [碰不到] 三条 | 承认，并装定期对账（`verify`） |

## 边界：它只管经过 agent 的路径

你在服务器上直接 `python run.py`、手工 `vim results.json`、在表格里改个数——全在 skill 之外。

所以真实防护范围 = **经过 agent 的操作**。越依赖 agent 跑实验，它越有效；越自己上手，它越接近一张废纸。这不是缺陷，是适用范围，得提前知道。

## 防不了的地方，用什么兜

1. **改流程 > 加校验 > 加字段。** 加字段是记录问题，改流程是消灭问题。
2. **降低正确路径的成本，而不是提高错误路径的代价。** 16 个必填字段的账本三周后被放弃；4 个必填的能用一年。所以：`n_total` 从 manifest 取、`queries_sha` 自动算、`script_sha` 从 git 取、`ran_at`/`host` 自动填、`fail_reason` 自动统计。人真正要判断的只有 `judge_version` 和 `prompt_cond`。
3. **把沉默失败改成响亮失败。** 每季度跑一次 `verify`，把报告里所有数字抽出来回账本找。它不阻止编，但保证编的东西在下一次被抓住。
